> 依据：`docs/PRD.md` **v1.0 开发版** · `docs/design/guitar-home/`（14 份页面设计稿 + `design-spec.md` **v2.0**）· 2026-09-11 代码审查  
> 本轮约定（沿用）：**不做旧测试数据迁移**——开发前清空数据库测试数据与 COS 存储桶，按新模型重新初始化；前置关系统一走 `prerequisites` 通用表，**允许成环、不做环判定**；COS 分片直传协议不变。**内容删除策略（2026-09-12 定稿，PRD §4.8）：物理删除 + 引用直接消失 + 作业仅存标题快照（零引用），全站不统计学习进度/收看数据。**

## §0 现状审查：必须修正的失误

**问题**：M0~M4 的功能开发没有按设计稿实现前端，视图层与设计稿是两套体系。

证据（已核对代码，非推测）：

- 设计稿的组件类在 `frontend/app/globals.css` 中**全部缺失**：`.nav-inner`、`.gsearch`、`.avatar`、`.card`、`.box-head`、`.pl-item`、`.frow`、`.brow`、`.filters` 均为 0 处定义
- 已实现页面自造了一套类名：`track-card`、`track-card-grid`、`track-hero`、`track-search`、`hero`、`hero-button`、`assignment-block`、`video-section`、`message-list` 等
- 后果：页面结构、间距、组件形态与设计稿不一致，设计稿的视觉语言（纸底 + 咖啡描边盒子 + 橘色强调 + 绿色仅点睛）没有落地

**修复策略**：不推倒重来。把设计稿当"样式源"分三层补齐，再逐页替换视图层。**功能逻辑与接口不动**。

| 层      | 做什么                                                                                                                                             | 产出物      | 完成标志               |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------- | ------------------ |
| L1 令牌  | 从 `design-spec.md` **v2.0** 抄 CSS 变量进 globals.css（`--white`/`--ink`/`--ink-2`/`--ink-3`/`--coffee`/`--orange`/`--hair`/`--hair-2`/`--glass`/`--glass-line`/`--ease` 等，另含 §3.2 格纹底饰伪元素）                                          | 变量层      | `grep` 到全部 token   |
| L2 组件类 | 从设计稿 `<style>` 抄共用类：`nav/nav-inner/nav-links/nav-right/logo/gsearch/avatar`、`card/grid`、`box/box-head`、`pl-item`、`frow`、`brow`、`filters`、`rise` | 全局 CSS 类 | 上述类名全部存在           |
| L3 组件  | 抽出 `AppNav`、`ContentCard`、`PanelBox`、`ListRow`、`FiltersBar` 五个 React 组件（`frontend/components/ui/`）                                              | 复用组件     | 五个组件可独立渲染且视觉与设计稿一致 |

> 顺序纪律：**L1→L2→L3 一次做完，再逐页返工**。基建未完成前不要改任何页面，否则每页都要改两遍。

## §1 硬性复用约束（写进每次派工）


### 1.1 COS 分片直传 —— 只许调用，不许重写

> 业务口径见 PRD §5.5。这是本项目复用优先级最高的模块，任何涉及上传的任务卡都必须遵守本节。

| 层     | 文件                                               | 已有能力                                                                      | 允许的改动                                                             |
| ----- | ------------------------------------------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 前端上传  | `frontend/components/uploadVideo.js`             | 校验常量、`validateUploadForm`、`uploadVideoByMultipart`（8MB 切片/并发/进度/失败 abort） | **无**（原样调用；分 P = 对每个 P 循环调用一次）                                    |
| 前端小文件 | `frontend/lib/api.js` → `uploadBlobWithProgress` | 封面、附件、PDF 预签名直传                                                           | **无**                                                             |
| 后端    | `backend/src/videos.routes.js` 四个 multipart 接口   | create / part-url / complete / abort                                      | 仅按业务需要加内容类型/归属参数，生成 `tracks/...`、`kp/...` key 前缀；**不改变分片协议与直传流程** |
| 后端    | `backend/src/storage.js`                         | 预签名、HeadObject 校验、删除、列对象                                                  | **无**（清空存储桶属初始化步骤）                                                |

## §4 执行纪律

1. **一次一张任务卡**，自检通过再开下一张；提交信息带任务号（如 `M3 曲目库按设计稿返工`）
2. **每页改完打开对应设计稿 HTML 逐块比对**：导航、卡片比例、盒子描边、行高、按钮。判断标准只有一条——**和设计稿长得一样**，不是"看起来还行"
3. **UI 与功能不混做**：返工阶段只改视图层，发现功能问题记下来另开卡
4. **上传相关改动必须在提交信息中单独说明**（改了哪个参数、为什么），便于回溯
5. 页头/登录类改动完成后，**四个角色各登录一次截图自检**（游客、学员、老师、教导主任）

> 工作量估计：M0~~M9 合计约 \*\*11~~15 个工作日\*\*（含 UI 返工），实际取决于现有功能逻辑可复用比例。
