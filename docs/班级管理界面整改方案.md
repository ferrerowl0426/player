# 班级管理界面整改方案

> 范围：`/admin/classes`  
> 对照来源：`docs/PRD.md` §2.2 / §2.4 / §2.6 / §4.9 / §5.7 / §8、`docs/design/guitar-home/class-manage.html`、当前实现 `frontend/app/admin/classes/page.js` 与 `frontend/app/admin/classes/page.module.css`。  
> 页面角色：仅教导主任。老师、学员、游客访问时应被权限拦截或重定向，不得渲染管理内容。

---

## 1. 总体结论

当前 `/admin/classes` 的视觉骨架已经接近设计稿：上方账号操作区、上排教导主任/老师列表、下排班级/学员联动列表、统一弹层和 toast 均已具备。但功能实现与设计稿存在若干高风险不一致，尤其是编辑资料链路、数据持久化链路、班级删除规则和页面中的运行时变量问题。

| 模块 | 当前还原度 | 主要问题 |
| --- | :-: | --- |
| 页面骨架 | 80% | 三块主体布局基本一致；当前下方区头多出“班级数/学员数”及本班搜索，设计稿主区头更简洁 |
| 账号列表 | 65% | 已有搜索、状态、重置/停用/删除，但当前实现没有“编辑”按钮，设计稿要求账号资料可编辑 |
| 班级列表 | 65% | 有联动和删除，但缺少设计稿明确的班级编辑、停用状态展示/操作一致性 |
| 新建账号 | 70% | 弹层结构基本具备，但账号校验仍强制 11 位手机号，和 PRD“纯数字、不限位数”冲突；密码口径也被改成只能系统生成 |
| 编辑资料 | 20% | 当前 React 页面没有真正渲染编辑资料入口/编辑资料弹层；设计稿要求昵称、密码、老师班级、学员转班均可编辑 |
| 班级新建/编辑 | 60% | 新建要求强制负责老师，和设计稿“先建名字即可、老师可稍后设置”冲突；前端有 classForm memo 但无编辑班级入口 |
| 删除语义 | 55% | 班级删除提示说学员转为未分班，但 PRD建议删除前拒绝并提示先转移；需统一并以后端为准 |
| 权限与接口 | 70% | 页面入口权限已有，但 `reload()` 与初始化异常处理需细化，接口返回结构需固定 |

**整改重点**：先修页面运行时稳定性与 API/PRD 口径，再补齐编辑资料和班级编辑。不要继续增加演示态本地逻辑；所有账号、班级、分班操作都必须落到后端并在刷新后保持。

## 2. 与 PRD / 设计稿差异清单

### 2.1 P0：账号编辑能力缺失或不可达

**PRD / 设计稿要求**

- 账号列表包含学员、老师、教导主任分类。
- 每个账号可进行：编辑资料、重置密码、停用/恢复、删除。
- 编辑资料弹层：
  - 账号只读，不可更改；
  - 昵称可修改，≤10 字，仅中文/字母/数字/下划线；
  - 密码不显示明文，点击「重置密码」后才出现新密码并保存；
  - 老师显示所带班级；班级关系在班级编辑中维护；
  - 学员可转班，只属于一个班级。
- 初始超级管理员不可编辑、不可删除。

**当前实现**

- `AdminRow` 只接收 `onToggle/onReset/onDelete/onAssign`，没有 `onEdit`。
- 页面没有 `EditAccountModal`，无法修改昵称、账号资料或在弹层内完成密码重置。
- 当前教导主任/老师列表只有“设置班级、重置密码、停用、删除”。
- 当前学员行只有“重置密码、转班、停用、删除”。

**整改动作**

1. 在 `AdminRow`、`StudentRow` 增加「编辑」按钮；初始超级管理员的编辑按钮置灰。
2. 新增 `editAccount` state 与 `EditAccountModal`：
   - 账号字段 readOnly；
   - 昵称输入实时校验；
   - 默认只显示“已设置 · 不保存明文”和「重置密码」按钮；
   - 点击后显示新密码、随机生成、复制、保存/取消重置；
   - 老师显示所带班级 chips；学员显示单选班级。
3. 后端补齐管理员/学员资料更新接口；至少支持昵称更新，密码沿用 reset-password 接口。
4. 前端 `reload()` 后以服务端数据为唯一事实，不在本地修改对象后直接 `render`。

**验收**

- 三类账号均能打开编辑资料弹层；初始超级管理员不可编辑/删除。
- 修改昵称、转班、密码重置刷新页面后仍保留。
- 账号字段不可编辑，昵称遵循 PRD 字符规则。

### 2.2 P0：创建账号校验与 PRD 不一致

**PRD 要求**

- 账号：必填，纯数字，不限位数，全局唯一。
- 昵称：≤10 字，仅中文/字母/数字/下划线。
- 密码：5~30 位。
- 创建入口按角色区分：新建学员、新建老师、新建教导主任。

**当前实现**

- `submitCreateAccount()` 使用 `/^\d{11}$/`，强制 11 位手机号。
- `maxLength` 设为 11。
- 昵称只检查非空，`maxLength` 设为 12，未校验字符集/长度。
- 密码只能系统生成，和设计稿“可手动输入，也可随机生成”不一致。
- 页面同时存在顶部“新建学员”和下方“＋ 添加学员”两个近似入口，文案/职责不够统一。

**整改动作**

- 账号前后端统一校验：`^\d+$`，不限制位数；输入框不设 11 位 maxLength，可设置合理防御上限但不能与业务规则冲突。
- 昵称统一正则：`^[\u4e00-\u9fa5A-Za-z0-9_]{1,10}$`。
- 初始密码允许手动输入或随机生成；默认随机生成但可编辑。
- 账号冲突返回 409，并在字段附近显示错误，不只用 toast。
- 将“添加学员”改为“新建学员”或明确为“从其他班级转入”，不混用“添加/新建”。按照 PRD 新页面统一使用“新建”。

**验收**

- `123456` 等纯数字账号可以创建；字母、空格、特殊符号被拒绝。
- 1~10 位合法昵称可以保存，11 位或特殊符号被拒绝。
- 5~30 位密码可手动输入或随机生成。

### 2.3 P0：新建班级错误地强制负责老师

**设计稿要求**

- 新建班级弹层先填写班级名称即可。
- 负责老师可稍后在班级编辑中分配。
- 一个班级只能有一位负责老师；一个老师可负责多个班级。

**当前实现**

- `openCreateClass()` 默认带入第一个老师。
- `submitCreateClass()` 在没有 `teacherId` 时直接报错“请选择负责老师”。
- `ClassFormModal` 文案写“备注仅用于本次填写提示；后端当前仍要求负责老师”，与设计稿和 PRD 冲突。
- `createClass` 请求必须传 `teacherId`，后端 POST `/classes` 也强制校验老师。

**整改动作**

1. 前端：
   - 新建班级只要求名称；负责老师下拉增加“暂不分配”。
   - 删除“备注（选填）”输入，PRD 明确无备注模型。
   - 同一弹层支持新建/编辑，通过 `classForm.id` 区分标题和提交文案。
2. 后端：
   - `POST /api/admin/classes` 允许 `teacherId` 为空。
   - `PATCH /api/admin/classes/:id` 支持只改名、只换老师、取消分配。
   - 保证同一班级最多一个老师；一个老师可以绑定多个班级。
3. 统一文案：`新 建 班 级`、`创建班级`、`负责任老师（选填）` 或 `负责老师（可稍后设置）`。

**验收**

- 没有老师账号时仍可先创建班级。
- 新建后可在班级编辑中分配/更换/取消负责老师。
- 一个老师可被分配多个班级，一个班级不会出现两个负责老师。

### 2.4 P1：班级编辑按钮缺失，班级关系维护不可达

**设计稿要求**

- 班级行右侧有“编辑 / 删除”。
- 编辑班级支持改名、更换负责老师；无备注。
- 选中班级后右侧显示该班学员。
- 学员可转班，目标班级为单选。

**当前实现**

- 班级行只渲染删除按钮：`page.js` 中 `cls-row` 的 `.row-ops` 没有编辑按钮。
- 虽然存在 `updateClass` API 和 `ClassFormModal`，但没有 `openEditClass` 状态/入口。
- 班级编辑无法到达，负责老师只能通过“设置班级”批量操作间接修改。

**整改动作**

- 班级行增加「编辑」按钮，点击不触发行选中。
- `openEditClass(cls)` 初始化 `{ id, name, teacherId }`。
- 复用 `ClassFormModal`，标题改为 `编 辑 班 级`，按钮为 `保 存`。
- 保存后调用 `updateClass`，然后 `reload()`，保留当前选中班级。
- 编辑停用班级时允许保留当前负责老师，但禁止把新学员转入停用班级，需有清晰提示。

**验收**

- 每个非系统班级都能从列表进入编辑。
- 改名、换老师、取消老师后，左右列表和老师所带班级即时同步。
- 系统虚拟班级「未分班学员」不能编辑/删除。

### 2.5 P1：未分班学员与班级删除语义不一致

**PRD 要求**

- 学员只能属于一个班级。
- 可转入“未分班学员”虚拟班级。
- 班级删除前需处理学生归属：置空或拒绝二选一，PRD 建议拒绝并提示先转移学生。
- 删除学员是彻底删除数据；删除老师会清理带班关系。

**当前实现**

- UI 将所有班级候选都直接作为转班目标，没有“未分班学员”系统选项。
- `transferUserClass` 后端要求有效 `classId`，不能转入空班级。
- 班级删除确认文案说“班内学员将进入未分班学员”，但后端 `DELETE /classes/:id` 没有检查班内学生数量；数据库约束/级联行为未在页面层明确。
- 页面 `allStudents` 只遍历 `classes[].students`，如果后端没有把未分班学员挂在某个班级，候选列表可能漏人。

**整改动作**

推荐采用 PRD 建议的“有学生则拒绝删除”方案：

1. 后端 `DELETE /api/admin/classes/:id` 先查询学生数。
2. 学生数 > 0 时返回 409：`该班级仍有 N 名学员，请先转移学员后再删除`。
3. 学员转班接口支持目标为“未分班”（可用 `classId: null`，或后端提供明确的 `unassigned` 语义）；前端统一显示虚拟班级。
4. 只有空班级允许删除；删除确认弹层改为“班级为空后才可删除”。
5. `未分班学员`为系统班级：可查看/接收学员，但不可停用、删除、改名、分配老师。

如果业务最终坚持“删除班级自动置空学生”，必须同步修改 PRD，并补充事务、提示和审计记录；不能保留当前前后端相互矛盾的状态。

**验收**

- 有学员的班级点击删除返回明确提示且不删除。
- 学员转入未分班后，原班级计数、虚拟班级计数、右侧列表一致。
- 空班级删除成功；系统班级不可删除。

### 2.6 P1：班级停用能力在 React 页面缺失

**设计稿 / 现有 CSS 语义**

- 班级可停用/恢复。
- 停用班级保留师生，但不可作为新转班目标或加入新学员。
- 停用状态使用灰色/停用标签，操作需要确认。

**当前实现**

- `page.js` 的班级行只提供“删除”，没有停用/恢复按钮。
- `statusClass`、`statusText` 只用于账号，不用于班级。
- CSS 有 `.cls-row.off` 和 `.cls-row` 的停用视觉预留，但 API `updateClass` 目前仅改名/老师，未发现 class status 更新口径。
- 新建/添加学员的候选班级未过滤停用班级。

**整改动作**

- 先确认数据库 `teaching_classes` 是否已有 `status/is_active` 字段；没有则补字段并定义迁移。
- 后端新增或扩展 `PATCH /api/admin/classes/:id/status`，或在现有 PATCH 中支持 `isActive`。
- 班级行增加「停用/恢复」按钮及二次确认。
- 停用班级不可作为新建学员初始班级、转班目标、批量添加目标。
- 已在停用班级的学生保留原关系，可正常查看历史；恢复后恢复作为目标班级的资格。

**验收**

- 停用班级显示停用标签并排在正常班级之后。
- 停用班级不出现在可选转班目标中。
- 恢复后可重新作为目标班级。

> 若产品确认班级“不需要停用”而只允许删除，应从 PRD、设计稿和 CSS 同步删除停用语义，不能只在页面隐藏。

### 2.7 P1：页面运行时变量和初始化稳定性风险

**当前实现风险**

- `page.js` 第 363 行使用 `normalizedStudentKeyword`、`globalStudentMatches`，当前文件中未发现定义，班级管理页很可能在渲染班级区时触发 `ReferenceError`。
- 这类客户端异常会导致页面出现 Application error，表现为“页面打不开/无法跳转”。
- 初始化 `fetchAdminMe()` 非 super_admin 时重定向 `/admin/users`，这是正确方向；但 classes/admins 任一接口失败都会统一跳登录，用户无法判断是权限还是接口故障。

**整改动作**

1. 删除无实际需求的全局搜索变量，或补齐定义；当前设计稿只有本班学员搜索，不要求跨班定位。
2. 使用 `studentKeyword` 直接控制当前选中班级的学员列表；如果确实需要全局搜索，需在 PRD 增加规范后再实现。
3. 初始化拆分错误：
   - 401/403 → 权限引导或重定向；
   - 500/网络错误 → 页面内错误卡片 + 重试按钮；
   - 空数据 → 正常空态，不跳登录。
4. `reload()` 使用取消/竞态保护，避免快速切换班级后旧请求覆盖新状态。
5. 所有异步按钮增加 disabled/busy 状态，避免重复提交。

**验收**

- `npm run build` / 容器编译无错误。
- 打开 `/admin/classes` 不出现 `ReferenceError`。
- 无权限、接口异常、空数据分别展示正确状态。
- 快速连续编辑/删除不会出现旧数据覆盖新数据。

### 2.8 P2：区头和入口与设计稿不完全一致

**设计稿要求**

- 顶部直接提供：`＋ 新建教导主任`、`＋ 新建老师`。
- 下方联合框区头提供：`＋ 新建班级`、`＋ 新建学员`。
- 区块标题为「教导主任」「老师」「班级 / 学员」，下方分栏为「班级」「学员」。
- 设计稿没有本班搜索框，也没有“添加学员”批量转入流程。

**当前实现**

- 上方同时有“新建教导主任/老师/学员/创建班级”。
- 下方又出现“＋ 新建班级”“＋ 添加学员”和“搜索本班学员”。
- `AddStudentsModal` 是额外功能，设计稿没有对应入口；且内部依赖“当前接口未提供未分班列表”的临时说明。
- “创建班级”与“新建班级”两种文案并存。

**整改动作**

- 以设计稿为准保留四个核心入口：新建教导主任、新建老师、新建班级、新建学员。
- 若确需批量转班，另作为明确的“批量转班”能力，不伪装成“添加学员”。
- 去掉“当前接口未提供……”这类实现备注，不将技术限制写给最终用户。
- 统一按钮文案为“新建 / 编辑 / 保存 / 删除 / 停用 / 恢复”。
- 下方学员搜索只有在 PRD 确认需要时保留；保留则需定义是当前班级搜索还是跨班搜索，避免 `globalStudentMatches` 半成品。

**验收**

- 设计稿核心入口和页面标题逐字一致。
- 页面不出现技术实现提示、演示字样或“添加/新建”混用。

## 4. 接口与数据契约建议

### 4.1 账号资料

```http
PATCH /api/admin/users/:id
Content-Type: application/json

{ "nickname": "新昵称" }
```

```http
PATCH /api/admin/admins/:id
Content-Type: application/json

{ "nickname": "新昵称" }
```

建议统一返回：

```json
{
  "data": {
    "id": 1,
    "username": "13800001234",
    "account": "13800001234",
    "nickname": "新昵称",
    "role": "teacher",
    "status": "active"
  }
}
```

### 4.2 班级

创建班级时 `teacherId` 可为空：

```json
{ "name": "进阶二班", "teacherId": null }
```

编辑班级：

```json
{ "name": "进阶二班", "teacherId": 3 }
```

取消负责老师：

```json
{ "teacherId": null }
```

### 4.3 未分班

推荐使用 `class_id = NULL` 表示未分班，并由接口统一返回：

```json
{ "id": "unassigned", "name": "未分班学员", "is_system": true }
```

前端禁止把字符串 `unassigned` 直接当成数据库整数提交；API 层负责转换为 `null`。

## 5. 设计与交互细节

- 纯白底、下方渐显格纹、咖啡描边盒子、橙色标题标记保持不变。
- 列表正常状态不额外堆叠绿色“正常”标签；停用状态用灰/红色状态标签。
- 所有危险动作使用自定义确认弹层，不使用 `window.confirm`。
- 成功/失败使用统一 toast，toast 文案不能出现“演示：”。
- 弹层支持 Esc、点击遮罩关闭；提交过程中按钮 disabled。
- 账号列表、班级列表、学员列表都要有空态、加载态、接口错误态。
- 列表过长时仅列表容器滚动，页面主体不被撑破。
- 老师多班使用多选；学员转班使用单选；班级负责老师一班一人。
- 不向最终用户展示“当前接口未提供……”等开发备注。
