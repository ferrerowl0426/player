# 边界校验学习记录：上传视频表单

## 1. 为什么需要边界校验

上传视频功能不能只依赖用户“正常填写”。

用户可能会提交：

```txt
空标题
超长标题
超长介绍
null / undefined / NaN 这类无意义文本
过大的视频文件
过大的封面图片
伪装成图片或视频的其他文件
不支持的文件格式
```

所以需要做边界校验。

## 2. 前端校验和后端校验的区别

### 2.1 前端校验

前端校验主要是为了用户体验。

例如：

```txt
标题最多 120 个字
介绍最多 1000 个字
封面最大 5MB
视频最大 500MB
```

用户在页面上就能尽早看到提示。

但是前端校验不能作为真正安全保障，因为用户可以绕过浏览器页面，直接调用后端 API。

### 2.2 后端校验

后端校验才是真正可信的校验。

无论用户从哪里发请求，最终都必须经过后端。

所以本项目同时做了：

```txt
前端校验：提升体验
后端校验：保证安全和数据质量
```

## 3. 当前项目的校验规则

| 内容 | 规则 |
|---|---|
| 标题 | 必填，最多 120 个字 |
| 标题特殊值 | 不能是 null、undefined、NaN |
| 介绍 | 可选，最多 1000 个字 |
| 介绍特殊值 | 不能是 null、undefined、NaN |
| 视频 | 必填，最大 500MB |
| 视频格式 | mp4、webm、mov |
| 封面 | 必填，最大 5MB |
| 封面格式 | jpg、jpeg、png、webp |

## 5. 前端相关文件

前端的 `accept` 可以让文件选择框优先展示指定格式：

```txt

```

但注意：`accept` 不是安全措施，后端仍然必须再次校验。

## 6. 关于 null 字符串

真正的 JavaScript `null` 和用户输入的字符串 `"null"` 不一样。

表单里用户输入的是字符串。

所以如果用户把标题写成：

```txt
null
```

它本质上是一个普通字符串。

本项目为了避免无意义数据，主动拦截这些字符串：

```txt
null
undefined
NaN
```

并且大小写不敏感，例如：

```txt
NULL
Undefined
nan
```

也会被拦截。

## 8. 重要原则

记住一句话：

```txt
前端校验是为了体验，后端校验才是真正安全。
```

数据库也可以做最后一层兜底，例如标题字段使用：

```sql
title VARCHAR(120)
```

但最好不要等数据库报错后再提示用户，而是在后端提前给出友好的错误信息。

## 9. 直传对象存储时，前端文件元数据不可信

这次发现一个新的边界问题：当前项目使用浏览器直传对象存储，前端先把文件元数据提交给后端，例如：

```json
{
  "video": {
    "name": "demo.mp4",
    "size": 1024,
    "type": "video/mp4"
  }
}
```

但是这些字段都来自前端，不能完全信任。

攻击者可以伪造：

```txt
name = demo.mp4
size = 1024
type = video/mp4
```

然后实际通过预签名 URL 上传一个 1GB 的视频文件。

所以在直传 COS / MinIO / S3 这类对象存储时，后端不能只根据前端声明的 `size`、`type`、`name` 判断文件是否合法。

### 9.1 当前问题

当前 `/api/videos/multipart/create` 阶段做了大小和类型判断，但判断依据是前端提交的 JSON 元数据。

这类校验只能算：

```txt
体验校验
初步校验
减少普通误操作
```

不能算真正安全边界。

因为真正的文件内容没有经过后端，后端在创建上传任务时还不知道用户最终会 PUT 什么内容到对象存储。

### 9.2 更可靠的校验位置

更可靠的做法是在对象上传完成后，由后端向对象存储查询真实对象信息。

也就是使用 `HeadObject` 获取对象的真实属性，例如：

```txt
ContentLength：对象真实大小
ContentType：对象存储记录的内容类型
```

然后以后端查到的真实结果为准。

推荐流程：

```txt
1. 前端继续做文件大小、类型、扩展名校验，用于用户体验
2. 后端创建上传任务时继续做元数据基础校验，但不把它当成最终安全判断
3. 视频分片 complete 后，后端 HeadObject 查询真实视频大小
4. 如果真实视频超过 500MB，后端删除该视频对象，并返回错误
5. 封面 PUT 完成后，后端 HeadObject 查询真实封面大小
6. 如果真实封面超过 5MB，后端删除相关对象，并返回错误
7. 只有真实对象大小合法，才允许写入数据库
```

### 9.3 为什么 `/videos/complete` 也要检查

即使 `/multipart/complete` 已经检查过视频，`/videos/complete` 也应该再次检查视频和封面对象。

原因是 `/videos/complete` 是最终写数据库的入口。

最终入库前要确认：

```txt
videoKey 确实存在
coverKey 确实存在
视频真实大小没有超过限制
封面真实大小没有超过限制
key 前缀符合预期，例如 videos/ 和 covers/
```

这样可以防止绕过正常前端流程，直接调用后端接口写入非法对象地址。

### 9.4 学到的原则

直传上传的安全边界要后移到“对象已经上传完成之后”。

记住：

```txt
前端声明的文件元数据不可信。
对象存储返回的真实对象信息才更可信。
```

前端校验解决体验问题，后端最终校验必须基于服务端能验证到的真实状态。

## 10. 未完成 Multipart 分片需要生命周期兜底清理

当前上传视频组件在 [uploadVideo.js](file:///c:/Users/user/Desktop/播放器/frontend/components/uploadVideo.js) 中负责浏览器分片直传。

正常情况下，如果上传失败或用户主动取消，前端可以调用后端的 abort 接口，让后端执行 `AbortMultipartUpload`，避免对象存储里残留未完成分片。

但是这个清理不能只依赖前端。

因为用户可能会：

```txt
关闭浏览器
刷新页面
断网
电脑休眠
进程被杀掉
上传到一半直接离开页面
```

这些情况下，前端不一定有机会成功调用 abort 接口。

如果没有额外兜底，腾讯云 COS 里会残留大量未完成的 Multipart Upload 分片。它们虽然还没有合并成最终对象，但仍然可能占用存储空间并产生费用。

### 10.1 前端 abort 只能算尽力清理

前端可以做：

```txt
上传失败时调用 /api/videos/multipart/abort
用户点击取消时调用 /api/videos/multipart/abort
页面卸载时尽量触发清理
```

但页面卸载、浏览器关闭、网络断开这类场景不可靠。

所以前端 abort 只能算：

```txt
best effort
尽力清理
提升正常流程下的资源回收效果
```

不能作为唯一清理机制。

### 10.2 腾讯云 COS 应配置生命周期规则

更可靠的做法是在腾讯云 COS 存储桶配置生命周期规则，自动清理未完成的 Multipart Upload。

建议配置：

```txt
清理未完成的分片上传任务
AbortIncompleteMultipartUpload
保留 1 天或 3 天后自动终止
```

这样即使用户关闭浏览器，COS 也会在生命周期规则生效后自动清理残留分片。

### 10.3 后续优化方向

后续可以同时做三层清理：

```txt
1. 前端：上传失败或取消时主动调用 abort
2. 后端：提供可靠的 multipart abort 接口
3. COS：配置生命周期，自动清理过期未完成分片
```

如果要进一步优化，还可以在后端记录上传任务：

```txt
uploadId
videoKey
创建时间
上传状态
管理员用户
```

然后定时扫描超时未完成任务，主动调用 AbortMultipartUpload。

但对于当前项目，优先级最高的是在腾讯云 COS 控制台配置生命周期自动清理未完成分片。

### 10.4 学到的原则

直传对象存储时，资源清理不能只靠浏览器。

记住：

```txt
前端清理是不可靠的。
服务端清理更可靠。
对象存储生命周期规则是最终兜底。
```
