# 2026-10-04 服务器磁盘占满导致登录与图片异常复盘

## 背景

线上登录页出现两个现象：

1. 登录接口 `POST https://api.nxhguitar.com/api/auth/login` 返回 500，页面提示 `could not write init file`。
2. 登录页左侧装饰图显示异常，浏览器控制台报 `wc-metronome-tall.jpg net::ERR_CONTENT_LENGTH_MISMATCH`。

同时数据万象转码工作流已能触发，后端日志出现 `[ci-callback]`，但回调处理报错：

```txt
ReferenceError: getPublicUrl is not defined
at findVideoIdBySourceKey (/app/src/transcode.js:209:21)
```

---

## 排查过程

### 1. 先确认图片文件是否存在

服务器执行：

```bash
cd /root/player

ls -la frontend/public/guitar-home/
docker exec video_player_frontend ls -la /app/public/guitar-home/

curl -s -o /dev/null -w "%{http_code}  %{content_type}  %{size_download}\n" \
  http://127.0.0.1:3001/guitar-home/wc-metronome-tall.jpg

curl -s -o /dev/null -w "%{http_code}  %{content_type}  %{size_download}\n" \
  https://nxhguitar.com/guitar-home/wc-metronome-tall.jpg
```

结果：

- 仓库中存在 `frontend/public/guitar-home/wc-metronome-tall.jpg`；
- 前端容器中存在 `/app/public/guitar-home/wc-metronome-tall.jpg`；
- 本地直连前端返回 `200 image/jpeg`；
- 走域名也返回 `200 image/jpeg`。

因此排除“文件缺失 / 镜像缺 public 文件 / Nginx 404”。

### 2. 查看后端日志

后端日志显示两类错误：

```txt
ReferenceError: getPublicUrl is not defined
```

这是本地代码问题：`backend/src/transcode.js` 中 `findVideoIdBySourceKey()` 使用了 `getPublicUrl()`，但 import 漏写。

另一个错误：

```txt
error: could not write init file
file: 'relcache.c'
routine: 'write_item'
```

这是 PostgreSQL 写初始化缓存文件失败，通常由磁盘满、inode 满、数据目录不可写等引起。

### 3. 检查磁盘

服务器执行：

```bash
df -h
df -ih
docker compose -p video_player -f docker-compose.yml -f docker-compose.local.yml ps
```

关键结果：

```txt
/dev/vda2  40G  38G  0  100% /
```

根分区 100%，确认是磁盘占满导致 PostgreSQL 无法写缓存文件，从而登录接口 500。

### 4. 查找占用来源

执行：

```bash
docker system df

du -h --max-depth=1 /root/player 2>/dev/null | sort -h
du -h --max-depth=1 /var/log 2>/dev/null | sort -h
```

关键结果：

```txt
/root/player 127M
/var/log 3.3G
/var/log/journal 3.0G
Docker Images 4.272GB，RECLAIMABLE 2.128GB
```

项目目录占用很小，主要可清理对象是：

- systemd journal 日志：约 3G；
- Docker 未使用镜像：约 2.1G 可回收。

---

## 处理方式

### 1. 清理 Docker 无用对象

执行：

```bash
docker system prune -f
docker builder prune -af
```

清理后磁盘从 100% 降到约 91%，PostgreSQL 已具备恢复写入的空间。

### 2. 清理 systemd journal 日志

建议保留 200MB：

```bash
sudo journalctl --vacuum-size=200M
```

然后确认：

```bash
df -h
du -h --max-depth=1 /var/log 2>/dev/null | sort -h
```

### 3. 视情况清理未使用 Docker 镜像

如果空间仍偏紧：

```bash
docker image prune -af
df -h
docker system df
```

该命令删除当前容器不用的镜像，不删除运行中的容器、数据库 volume、MinIO/COS 数据。

### 4. 重启服务验证

先重启后端：

```bash
cd /root/player
docker compose -p video_player -f docker-compose.yml -f docker-compose.local.yml restart backend
```

如果仍报 `could not write init file`，再重启 PostgreSQL 和后端：

```bash
docker compose -p video_player -f docker-compose.yml -f docker-compose.local.yml restart postgres backend
```

本次用户反馈：清理后登录恢复正常，图片显示恢复正常。

## 同步发现的代码问题

### 1. 数据万象回调漏引入 `getPublicUrl`

现象：

```txt
ReferenceError: getPublicUrl is not defined
at findVideoIdBySourceKey (/app/src/transcode.js:209:21)
```

原因：`backend/src/transcode.js` 使用 `getPublicUrl(objectKey)` 反查 `videos.id`，但 import 中漏了 `getPublicUrl`。

本地修复：

```js
import { deleteFromBucket, getKeyFromPublicUrl, getPublicUrl } from './storage.js';
```

状态：本地已改，尚未推送 Gitee，需后续提交并部署 backend。

### 2. 数据万象回调口径改为“工作流完成回调”

用户确认控制台选择的是“工作流完成回调”，不是“任务完成回调”。正确原因：同一个工作流里有 720p、1080p 两个转码节点，如果用任务完成回调，第一个节点完成时就可能触发业务侧“转码完成/发布”逻辑，而另一个节点仍在处理中。

本地调整：

- `parseCiCallbackPayload()` 改为 `parseCiWorkflowCallbackPayload()`；
- 不再兼容旧任务完成回调测试数据；
- 一次回调解析全部 `JobsDetail`；
- 对每个转码节点分别判断 `720p/1080p`、校验产物路径和对象存在性、写入 `video_renditions`；
- 不在回调里做“发布视频”动作，只登记各清晰度 ready/failed 状态。

状态：本地已改，尚未推送 Gitee，需后续提交并部署 backend。

### 3. 登录页装饰图定位微调

本地已把：

```css
background: #ffffff url("/guitar-home/wc-metronome-tall.jpg") center/cover no-repeat;
```

改为：

```css
background: #ffffff url("/guitar-home/wc-metronome-tall.jpg") center top / cover no-repeat;
```

目的：让节拍器主体优先从顶部显示，避免装饰图裁切不理想。

状态：本地已改，尚未推送 Gitee。

## 后续运维建议：是否需要定期清理日志？

需要，但建议用“限制日志上限”的方式，而不是每次手动救火。

### 1. 配置 systemd journal 自动限额

编辑：

```bash
sudo nano /etc/systemd/journald.conf
```

建议增加或修改：

```ini
[Journal]
SystemMaxUse=300M
SystemKeepFree=1G
MaxRetentionSec=14day
```

重启 journald：

```bash
sudo systemctl restart systemd-journald
journalctl --disk-usage
```

含义：

- `SystemMaxUse=300M`：journal 日志最多占 300MB；
- `SystemKeepFree=1G`：磁盘至少预留 1GB；
- `MaxRetentionSec=14day`：最多保留 14 天日志。

### 2. 配置 Docker 容器日志上限

编辑或创建：

```bash
sudo nano /etc/docker/daemon.json
```

建议内容：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "50m",
    "max-file": "3"
  }
}
```

重启 Docker：

```bash
sudo systemctl restart docker
cd /root/player
docker compose -p video_player -f docker-compose.yml -f docker-compose.local.yml up -d
```

注意：重启 Docker 会短暂影响服务，建议低峰期操作。

### 3. 定期巡检命令

建议每周或每次部署前执行：

```bash
df -h
docker system df
journalctl --disk-usage
```

如果根分区使用率超过 85%，优先处理；超过 90% 时，不建议继续 `docker build`。

### 4. 临时手动清理清单

当磁盘不足时，按以下顺序清理：

```bash
# 清 journal，保留 200MB
sudo journalctl --vacuum-size=200M

# 清停止容器、悬空镜像、无用网络、构建缓存
docker system prune -f
docker builder prune -af

# 清未使用镜像
docker image prune -af

# 查看结果
df -h
docker system df
journalctl --disk-usage
```

---

## 经验结论

1. `could not write init file` + PostgreSQL `relcache.c write_item`，优先查 `df -h`。
2. 根分区 100% 会引起一串看似无关的问题：登录 500、资源传输异常、容器写缓存失败。
3. `ERR_CONTENT_LENGTH_MISMATCH` 不一定是前端代码问题，也可能是磁盘满导致代理/容器传输异常。
4. 40GB 服务器跑 Docker + Next.js build + PostgreSQL + 日志，必须限制 journal 和 Docker 日志大小。
5. 部署前最好保证至少 6-8GB 可用空间；如果低于 4GB，不建议继续 build。
