## 3. CI 回调未配置密钥时可被伪造 —— ✅ 已整改（代码），⚠️ 线上还未部署

### 现状（已按「验签通过才更新」实现）

`backend/src/transcode.js:231-250`：

```js
export function verifyCiCallbackRequest({ rawBody = '', signature = '', token = '', secret = '' }) {
  const expectedSecret = toText(secret);
  if (!expectedSecret) {
    return { ok: false, reason: 'unconfigured' };   // 没配密钥 → 一律拒绝
  }

  if (timingSafeEquals(toText(token), expectedSecret)) {
    return { ok: true, via: 'query-token' };
  }

  const providedSignature = toText(signature);
  if (providedSignature) {
    const expectedSignature = crypto.createHmac('sha256', expectedSecret).update(rawBody || '').digest('hex');
    if (timingSafeEquals(providedSignature, expectedSignature)) {
      return { ok: true, via: 'hmac' };
    }
  }

  return { ok: false, reason: 'invalid' };
}
```

关键点：

- **删除了旧的 `verifyCiSignature`**（那个实现是 `if (!secret) return true;`，正是问题描述里的漏洞），改为 `verifyCiCallbackRequest`：未配置密钥 → `ok: false, reason: 'unconfigured'`，路由返回 503；token / 签名不对 → 401。
- 比较使用 `crypto.timingSafeEqual`，避免时序侧信道。
- 回调路由 `backend/src/videos.routes.js:696-710`：密钥通过 `req.query.token` 或 `x-ci-callback-token` 头传入，另有 `x-ci-signature` / `x-cos-signature` HMAC 分支。

## 6. 老师停用后旧 token 还能执行管理操作 —— ❌ 未整改

### 现状

`backend/src/auth.js:74-108`（`requireRole`）：解析 JWT 后只做三件事——`payload.type` 校验、`payload.role` 是否在允许列表、`payload.status === 'disabled'` 判断，**全程不查数据库**：

```js
const payload = jwt.verify(token, config.auth.jwtSecret);
...
if (!allowedRoles.includes(payload.role)) { ... }      // 角色来自 token
if (payload.status === 'disabled') { ... }             // 状态来自 token（登录那一刻的快照）
```

`backend/src/auth.js:110-137`（`requireAdminSession`）更宽松：只校验 `type` 和角色，**完全不看 status**。
`backend/src/auth.js:139-145`：`requireAdmin` = `requireRole('teacher','super_admin')`，`requireSuperAdmin` = `requireRole('super_admin')` —— 所有管理接口都走这条链路。

而停用操作（`backend/src/admin.routes.js:764-772`）只更新数据库 `admins.status`，**不会让已签发的 token 失效**；token 有效期 7 天，所以老师被停用后，只要他这 7 天内没重新登录，旧 token 里的 `status` 仍是 `active`，管理接口全部放行。角色变更（老师←→教导主任）同理，7 天内不生效。

登录接口本身是对的：`admin.routes.js:247-298` 不拦停用账号，并在响应里返回 `status / isActive`，符合「停用老师仍可登录、看到停用提示」的要求。

### 整改方案（推荐 A）

**方案 A：鉴权时回查数据库（推荐）**

在 `requireRole` / `requireAdminSession` 里，`jwt.verify` 成功后加一次主键查询：

```js
const current = await pool.query('SELECT role, status FROM admins WHERE id = $1', [payload.adminId]);
if (current.rowCount === 0) {
  clearAdminCookie(res);
  res.status(401).json({ message: '登录已过期，请重新登录' });   // 账号已被删除
  return;
}
const { role, status } = current.rows[0];
// 角色以数据库为准，升/降权即时生效
if (!allowedRoles.includes(role)) { res.status(403).json({ message: '没有执行此操作的权限' }); return; }
if (status === 'disabled') { res.status(403).json({ message: '此账号已停用，不能执行管理操作' }); return; }
```

要点：

- 需要把 `requireRole` / `requireAdminSession` 改成 `async`；`auth.js` 需 import `pool`（注意别造成循环依赖：`db.js` 不引用 `auth.js`，可以直接 import）。
- 角色判断改用**数据库里的 role**，而不是 token 里的 role，避免「降权后 7 天内仍是旧权限」。
- **保留停用老师可登录、可看到停用提示**：登录接口不拦（现状已满足）；`requireAdminSession` 建议只在「账号被删除」时拒绝，停用状态仍然放行，只把 `req.admin.status` 更新为最新值，供前端展示停用提示。
- 性能：每个管理请求多一条主键查询，当前量级可忽略。若日后要压，可加 30~60 秒 TTL 的内存 Map 缓存，并在停用/改角色时主动清掉对应条目。

**方案 B：短 token + 刷新**：把 token 有效期缩短、加 refresh 机制。改动面大，本项目当前规模不建议。

## 7. 替换视频后 renditions 仍指向旧文件 —— ❌ 未整改

### 现状

`backend/src/videos.routes.js:1057-1108`（`PUT /api/videos/:id`）在一个事务里只做了：

```js
UPDATE videos
   SET title = $1, description = $2,
       video_url = COALESCE($3, video_url),
       cover_url = COALESCE($4, cover_url)
 WHERE id = $5
```

随后 `:1101` 删除旧对象（`oldKeysToDelete` 只包含旧的 `video_url` / `cover_url` / 被替换的附件 key），**全程没有触碰 `video_renditions`**。

对比新建视频时会调用 `createInitialRenditions`（`backend/src/transcode.js:25-45`），把 `source` 写成 `ready`、`720p` / `1080p` 写成 `processing`。替换视频时这一步被跳过了。

后果（就是清单里说的问题）：

1. `video_renditions` 里 720p / 1080p 仍是旧的 `ready` + 旧地址（指向已删除的旧文件）→ 播放器画质菜单里选 720P / 1080P 会**死链**。
2. 旧转码产物在桶里成了孤儿；因为 `oldKeysToDelete` 不含它们，**不会被清理**。
3. 新视频即使被工作流转码了，回调写回时用的是「源 key 反查 videos.id」，能覆盖到旧记录，但中间这段时间状态是错的。

### 整改方案

在 `videos.routes.js` 的替换事务里补两步（只在**本次确实换了源视频**（`videoKey` 非空）时执行）：

1. **重置档位**：把该视频的 720p / 1080p 重置为空 + `processing`：

```js
await client.query(
  `UPDATE video_renditions
      SET video_url = '', file_size = 0, status = 'processing', updated_at = CURRENT_TIMESTAMP
    WHERE video_id = $1 AND quality = ANY($2::text[])`,
  [videoId, ['720p', '1080p']]
);
```

2. **重建 source 档**：调用 `createInitialRenditions(client, { videoId, sourceUrl: getPublicUrl(videoKey), sourceSize: Number(videoHead.ContentLength || 0) })`（`videoHead` 在 `:1024` 已经拿到，直接复用）。

   ⚠️ 注意：`createInitialRenditions` 里 720p / 1080p 用的是 `ON CONFLICT DO NOTHING`，**不会**把已有行重置，所以第 1 步的 UPDATE 必须先执行，或把该函数的语义改成「重置式 upsert」。

3. **清理旧产物**：替换前先查一次 `SELECT video_url FROM video_renditions WHERE video_id = $1 AND quality <> 'source'`，把得到的 key 并入 `oldKeysToDelete`（`:1050-1056`），否则 `transcoded/` 下会持续堆积孤儿文件。

4. 只改标题 / 描述 / 封面（`videoKey` 为空）时，**不要动** renditions。

补充：重置成 `processing` 期间前端不会白屏——`frontend/components/VideoPlayer.js` 在没有 ready 档位时会回落到原画 `source`。

## 8. 图书馆 PDF 不按真实文件大小复核 —— ❌ 未整改

### 现状

`backend/src/library.routes.js:189-234`（`POST /api/library`）：

```js
const fileSize = size(req.body.fileSize);     // :197 直接采信前端上报
...
if (fileSize > PDF_MAX_SIZE) { ... }          // :217-220 用前端上报的数字判断
...
INSERT INTO library_resources (..., file_size, ...) VALUES (..., fileSize, ...)   // :229 前端数字落库
```

`:222` 的 `await ensureObjectExists(fileKey)` 只用来确认对象存在。而 `backend/src/storage.js:137-146` 里 `ensureObjectExists` 返回的就是 **HeadObject 的完整结果**（含 `ContentLength`），所以真实大小其实是现成的，只是没被用起来。

也就是说：只要改一改前端请求里的 `fileSize`（或构造请求），就能绕过 500MB 限制，且列表页展示的大小也是假的。

`/upload-url`（`:155-186`）里的 `fileSize` 同样只能当提示用，`PATCH /:id`（`:243`）不接收新文件，不受影响。

### 整改方案

在 `POST /` 里改成「以存储端真实大小为准」：

```js
if (!cover) { ... }                            // 现有校验保持

const head = await ensureObjectExists(fileKey);          // 已存在，复用返回值
const realSize = Number(head.ContentLength || 0);

if (realSize > PDF_MAX_SIZE) {
  await deleteFromBucket(fileKey).catch(() => {});       // 顺手清掉超限文件，避免留孤儿
  res.status(400).json({ message: 'PDF 文件不能超过 500MB' });
  return;
}
```

随后 INSERT 时用 `realSize` 替换 `fileSize`（前端上报值仅用于上传前的即时提示）。

建议一并处理：

- 如果封面上传也走同一个桶（`library/covers/`），对 `cover` 字段同样做 HeadObject 复核（封面 10MB）；非本站桶的 URL 跳过。
- 失败分支记得 `rollback`（现有 `catch` 已处理）并把已上传的对象清掉，避免 500MB 以上的文件在桶里长期占空间。

## 9. 清理脚本引用集合不完整，可能误删有效转码文件 —— ❌ 未整改

### 现状

`backend/scripts/clean-orphan-objects.js:10-25` 的引用集合只收集了两张表：

```js
SELECT video_url, cover_url FROM videos
UNION ALL
SELECT file_url, cover FROM library_resources WHERE file_url <> ''
```

`:29-34` 的扫描范围只有两个前缀：

```js
const bucketKeys = [
  ...(await listBucketKeys('videos/')),
  ...(await listBucketKeys('covers/'))
];
```

缺失的引用：

- `video_renditions.video_url`（**source / 720p / 1080p 三档都在这里**）
- `video_attachments.file_key`
- 曲目区 / 知识点区各表的封面字段（`track_points.cover`、`track_collections.cover`、`knowledge_points.cover`、`knowledge_collections.cover` 等，实际字段名需再核对）

风险判断（按现状精确说）：

- `video_renditions` 的 `source` 档地址与 `videos.video_url` 一致，所以 source 目前不会被误判。
- 新产生的 720p / 1080p 产物在 `transcoded/` 下，而脚本**还没扫** `transcoded/`，所以今天不会误删；但反过来，这些前缀下的孤儿文件也**永远清不掉**。
- 真正的问题是**顺序**：一旦以后把扫描范围扩到 `transcoded/`、`attachments/`、`tracks/`、`knowledge/`（这是迟早的事，现在 P 视频就在 `tracks/`、`knowledge/` 下），而引用集合没同步补全，就会立刻开始误删有效文件。`covers/` 已经在扫描范围内，所以「哪些表的封面落在 `covers/` 下」必须先盘点确认——若存在未收集的封面，今天就有误删。

### 整改方案

**第一步：补全引用集合**（在动扫描范围之前完成）。逐表确认字段后统一按 `getKeyFromPublicUrl` 归一化：

| 来源 | 字段 |
|---|---|
| `videos` | `video_url`、`cover_url` |
| `video_renditions` | `video_url`（新增） |
| `video_attachments` | `file_key`（新增） |
| `library_resources` | `file_url`、`cover`、`file_key` |
| `track_points` / `track_collections` | 封面字段（核对实际列名） |
| `knowledge_points` / `knowledge_collections` | 封面字段（核对实际列名） |
| 曲目 / 知识点附件表 | 附件 key 字段（核对实际列名） |

**第二步：再扩扫描前缀**，按需加 `attachments/`、`tracks/`、`knowledge/`、`transcoded/`；每加一个前缀，都要先回到第一步确认该前缀下的引用是否已全部收集。

## 10. 一次作业推送批量插入没有事务 —— ❌ 未整改

### 现状

`backend/src/admin.routes.js:1301-1311`（`POST /api/admin/users/:userId/assignments`）：

```js
const operationResult = await pool.query(`SELECT nextval('user_assignments_operation_id_seq') AS operation_id`);
const operationId = operationResult.rows[0].operation_id;
const insertedRows = [];
for (const item of newObjects) {
  const result = await pool.query(`INSERT INTO user_assignments (...) VALUES (...)`);
  insertedRows.push(result.rows[0]);
}
if (newObjects.length === 0 || (legacyMessage && !practiceRequirement && !submitRequirement)) {
  const result = await pool.query(`INSERT INTO user_assignments (...) VALUES (...)`);
  insertedRows.push(result.rows[0]);
}
```

每条 INSERT 都用 `pool.query` 独立执行，没有 `BEGIN` / `COMMIT`。老师一次推送 5 个内容时，如果第 3 条失败（超时、连接断开、约束冲突），前 2 条已经落库，后 3 条没有，用户看到的是失败提示，但库里留下**半批作业**；而且这些记录用的是同一个 `operation_id`，取消作业时会按 operation 粒度操作，半批数据会让取消/删除行为也变得诡异。

### 整改方案

把「取 operation_id + 全部 INSERT」包进一个事务（校验逻辑保持在事务外，`:1259-1299` 已经在插入前完成，符合要求）：

```js
const client = await pool.connect();
try {
  await client.query('BEGIN');

  const operationResult = await client.query(
    `SELECT nextval('user_assignments_operation_id_seq') AS operation_id`
  );
  const operationId = operationResult.rows[0].operation_id;
  const insertedRows = [];

  for (const item of newObjects) {
    const result = await client.query(`INSERT INTO user_assignments (...) VALUES (...)`, [...]);
    insertedRows.push(result.rows[0]);
  }

  if (newObjects.length === 0 || (legacyMessage && !practiceRequirement && !submitRequirement)) {
    const result = await client.query(`INSERT INTO user_assignments (...) VALUES (...)`, [...]);
    insertedRows.push(result.rows[0]);
  }

  await client.query('COMMIT');
  res.status(201).json({ data: { operationId, rows: insertedRows } });
} catch (error) {
  await client.query('ROLLBACK');
  throw error;
} finally {
  client.release();
}
```

要点：

- 事务里**不要**再混入外部 IO（HeadObject、COS 调用等），只做数据库操作。
- `nextval` 在回滚后不会回收序号，属于正常现象（序号出现跳号），可以接受。
- 参考实现：`library.routes.js:189-241` 就是同一套 `client + BEGIN/COMMIT/ROLLBACK` 写法，风格保持一致。
