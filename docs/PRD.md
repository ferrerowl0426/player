## 1. 产品定位与范围

面向吉他教室的**内部教学视频平台**。三类使用者：

- **教导主任**：上传与维护全部教学内容（曲目、知识点、资料），管理账号与班级
- **老师**：管理本班学生，查看学习记录，推送作业并填写练习要求与提交要求
- **学员 / 游客**：看视频、下载资料，学员额外能看到老师布置的作业

范围边界：

- 账号**由教导主任统一发放**，无注册、无自助改密、无找回密码
- 不收费、不做评论弹幕、不做视频转码/多清晰度、不做数据看板
- 前端 Web（校园/教室内使用），设计方案为桌面优先；移动端仅要求不崩（见 §3.4 响应式）

## 2. 角色、权限与账号

### 2.1 角色定义

| 角色   | 说明       | 存储位置                              |
| ---- | -------- | --------------------------------- |
| 游客   | 未登录访问者   | 无账号（前端 `guest.js` 控制）             |
| 学员   | 付费/在册学生  | `users` 表                         |
| 老师   | 带班教师     | `admins` 表，`role = 'teacher'`     |
| 教导主任 | 内容与账号管理者 | `admins` 表，`role = 'super_admin'` |

> 实现提示：老师与教导主任**同表不同 role**，登录后由 `role` 字段决定前端口径；学员独立在 `users` 表，登录走 `/api/user/login`。

### 2.2 权限矩阵

| 能力 / 板块                        |  游客 |  学员 |     老师    | 教导主任 |
| ------------------------------ | :-: | :-: | :-------: | :--: |
| 播放视频、下载资料                      |  ✅  |  ✅  |     ✅     |   ✅  |
| 曲目区 / 知识点区 / 图书馆 浏览            |  ✅  |  ✅  |     ✅     |   ✅  |
| 内容上传 / 编辑 / 删除（曲目、知识点、合集、P、资料） |  ❌  |  ❌  |     ❌     |   ✅  |
| 首页（作业 + 练习要求 + 提交要求）      |  ❌  |  ✅  |     ❌     |   ❌  |
| 我的历史作业                         |  ❌  |  ✅  |     ❌     |   ❌  |
| 学生管理                           |  ❌  |  ❌  |  ✅ 限本人班级  | ✅ 全部 |
| 布置作业 / 练习要求 / 提交要求        |  ❌  |  ❌  | ✅ 限本人班级学生 | ✅ 全部 |
| 停用 / 恢复本班学生                    |  ❌  |  ❌  |     ✅     |   ✅  |
| **标记学生**（打标记 / 取消 / 一键清除）      |  ❌  |  ❌  |     ❌     |   ✅  |
| 班级管理（建账号、分班、停用/删除账号）           |  ❌  |  ❌  |     ❌     |   ✅  |

前端**不渲染越权入口**，后端**每个接口独立鉴权**（前端隐藏不算安全措施）。

### 2.3 核心规则

1. **内容权与管理权分离**：老师**零内容权限**，一切内容增删改仅教导主任。
2. **老师与教导主任没有首页**：老师登录后默认进入「学生管理」；教导主任登录后默认进入「曲目区」。
3. **游客没有首页**：游客入口进入后默认落在「曲目区」，只能播放与下载。
4. **学生管理是同一个页面**：顶部两个筛选条件——**班级 + 学生**（学生可搜索）。老师进入时班级筛选**锁死为本人所带班级**（一师多班时可多选）；教导主任两个筛选均自由。选定学生后的**作业历史记录与布置作业**为同一页面内的组件；作业历史记录与学员「我的历史作业」共用同一份数据模型和记录组装规则，只按角色控制可见操作与跳转权限。
5. **分班结构**：一个老师可对应多个班级（`teacher_classes` 多对多）；一个学生只属于一个班级（`users.class_id`）。
6. **内容全局共享**：教导主任上传的曲目、知识点、资料对所有角色可见（游客可播放/下载）。
7. **停用 ≠ 删除**：被停用账号仍可正常登录，只是进入受限状态（见 §2.6）。
8. **详情页不做学习进度**：无「已看 ✓」、无进度条/百分比；前置知识点也不做「未学习」标记（**此项与 design-spec v2.0 §2.4 的绿色未学习圆点冲突，以用户要求为准：本轮不实现该状态标记**）。

### 2.4 账号模型

四要素，`users` 与 `admins` 两张表字段口径一致：

| 字段              | 类型            | 说明                             |
| --------------- | ------------- | ------------------------------ |
| `role`          | varchar       | 学员 / 老师 / 教导主任（`users` 表隐含为学员） |
| `account`       | varchar, 全局唯一 | **登录账号**（如手机号），登录凭据之一          |
| `nickname`      | varchar       | 昵称，**仅界面展示**（学生列表、留言署名）        |
| `password_hash` | text          | 密码（bcrypt）                     |
| `status`        | varchar       | `active` / `disabled`          |

规则：

- 登录方式 = **账号 + 密码**，昵称不参与登录（此前把 `username` 当登录名是错的）
- 现有 `username`（如 `student_a1`）**本质是昵称**，保留展示用途
- 本轮**不做旧数据迁移**：开发前清空测试数据，按新模型重新初始化（见开发计划 M0）
- **账号字段边界校验**（新建与重置密码同规则，详见 §4.9）：
  - `nickname`：必填，≤ 10 字，仅允许中文 / 英文字母 / 数字 / 下划线（禁空格与其他符号）
  - `account`：必填，**纯数字**，**不限位数**（兼容海外学员手机号），全局唯一
  - `password`：必填，**5 ~ 30 位**

### 2.5 登录与会话

- 三类身份**共用登录入口**语义：学员走 `/api/user/login`，老师/教导主任走 `/api/admin/login`；登录页按同一界面呈现，提交后由后端返回的角色决定跳转
- 会话凭据沿用现有 cookie 机制（`auth.js`），不做 token 改造
- 登录成功后跳转规则：学员 → 首页 `/`；老师 → `/admin/users`；教导主任 → `/tracks`
- 游客入口：登录页提供「游客浏览」入口，进入后落 `/tracks`

### 2.6 停用机制

`status = 'disabled'` 的账号**仍可登录**，行为如下：

| 角色   | 表现                                                                 |
| ---- | ------------------------------------------------------------------ |
| 学员   | 仍可浏览视频、下载资料；**首页**显示提示条；**我的历史作业**页显示提示条（文案见 §8）                   |
| 老师   | 仍可登录，`/admin/users` 内容区替换为停用提示（标题 + 正文见 §8），**不可执行任何管理操作**，接口层同样拒绝 |
| 教导主任 | 可正常登录；默认收起内容管理入口（保留只读浏览），是否保留管理权由站长决定                              |

操作权限与入口：

- 停用 / 恢复**学员**：本班老师 或 教导主任
- 停用 / 删除**老师、其他教导主任**：仅教导主任
- 恢复与停用**同入口，一键切换**（`PATCH /api/admin/users/:id/status`）
- 停用老师后，其带班关系保留（`teacher_classes` 不清空），恢复后原样生效

### 3.4 视觉规范引用（摘要，细节以 design-spec.md v2.0 为准）

- **页面底色纯白** + 焦糖咖啡格纹底饰（下浓上淡、页头处消失）；**旧版米黄纸底已废除**

- **类型标签 `.ptag` 配色变体**（2026-09-15 补齐于 `design-system.css`，此前全部回落为橘色）：`t-kset` 知识点集（深棕实底）/ `t-kp` 单知识点（咖啡 + 虚线边）/ `t-track` 单曲目（绿实底）/ `t-score` 曲谱集（金实底）/ `t-book` 图书（浅橘 + 虚线边）。chip 结构统一为 `<span class="nm"><span class="ptag t-xxx">类型</span>标题</span>` + `✕` 移除按钮（按钮需 `aria-label`）

- 响应式：≤1024px 网格降列、详情页恢复页面滚动；≤640px 页边距收窄、隐藏导航链接
- 登录页为独立水彩明信片风格，不适用上述背景与导航规范

### 3.5 合集详情页 · 收录网格的教导主任操作层（2026-09-15 定稿）

**适用范围**：`/tracks/collections/[id]`（曲谱集详情）与 `/knowledge/collections/[id]`（知识点集详情）的「收录单课」网格。**仅教导主任（`super_admin`）**可见；老师/学员/游客不渲染。

**实现机制（全站唯一口径，新增页面不得另写一套）**

1. 页面调用 `fetchCurrentViewer()` 取当前身份 → `isSuperAdmin = viewer?.role === 'super_admin'`
2. `document.body.classList.toggle('dean', isSuperAdmin)`
3. 收录网格的 `ContentCard` 传 `actions`：`查看详情` / `编辑` / `删除`
4. 显隐完全交给全局 CSS：`.card .ops { display:none }` + `body.dean .card:hover .ops { display:flex }`；`ContentCard` 内部固定渲染 `<div className="ops">{actions}</div>`

| 按钮  | 跳转 / 行为                                                       |
| --- | ------------------------------------------------------------- |
| 查看详情 | 曲目 → `/tracks/[id]`；知识点 → `/knowledge/[id]`                   |
| 编辑  | 曲目 → `/admin/tracks?id=[id]`；知识点 → `/admin/knowledge?id=[id]` |
| 删除  | 打开第一层确认弹层（见下）                                                  |

**删除 = 两段确认**

- 第一层「删除确认」：正文说明**「移出本合集只解除收录关系，单课与其视频保留；彻底删除会连同全部分段与视频一并删除」**；按钮 = 取消 / **移出本合集** / **彻底删除**
- 选「彻底删除」→ 第二层「彻底删除确认」：按钮 = 取消 / **确认删除**
- 反馈用全局 toast（1.6s 自动消失）：移出成功 → 「移出成功」；彻底删除成功 → 「删除成功」
- 移出调 `PATCH /api/{tracks|knowledge}/collections/:id/{tracks|points}`（传入剩余 id 数组）；彻底删除调 `DELETE /api/{tracks|knowledge}/:id`
- 任一动作完成后重新拉取合集详情并重置到第 1 页

> ⚠️ **历史 bug（已修，勿复发）**：两个合集详情页原先**从未调用 `fetchCurrentViewer()`**，`viewer` 恒为 guest，导致 `body.dean` 不会打上、也不会传 `actions`，设计稿的悬停操作层完全不出现。任何带卡片操作层的页面都必须走上面 4 步。

## 4. 内容模型

### 4.1 三段式对象层级

```
单课（track_point / knowledge_point）   例：卡农 / 1645 和弦进行
 ├─ 封面（1:1，必填）
 ├─ 简介
 ├─ P1 ── video（复用 videos 表）
 ├─ P2 ── video
 └─ P3 ── video
合集（track_collection / knowledge_collection）  例：周杰伦专辑 / 指弹入门
 ├─ 封面（1:1，必填）
 ├─ 简介
 └─ 收录多个单课（多对多：track_collection_items / knowledge_collection_items）
```

要点：

- **P 不是独立内容**：P 依附单课存在（`track_parts` / `knowledge_parts`），本身**没有封面、没有简介页**
- **单课可同时属于多个合集**，互不影响；删除合集只删关联，不删单课
- **删除单课时**：同步删除其 P 关联的 `video` 与 COS 对象（沿用现有删除一致性链路）

### 4.2 封面规则

| 对象             |          封面          |
| -------------- | :------------------: |
| 单课（单曲目 / 单知识点） |        需要，1:1        |
| 合集（曲谱集 / 知识点集） |        需要，1:1        |
| P 分段           | **不需要**（展示时用所属单课的封面） |

- 上传单课/合集时封面**必填**（沿用现有封面必填校验）
- 推送单个 P 时，卡片展示**所属单课的封面**
- 因此 `track_parts` / `knowledge_parts` **不设 cover 字段**

### 4.3 前置关系

- 详情页「前置知识点」可选**四种对象**：单曲目、曲谱集、单知识点、知识点集
- 点击前置项跳转到对应详情页（合集类前置跳到合集详情页）
- **不做环判定**：老师在后端手动维护，出现环时按实际跳转链浏览，不做检测与提示
- 存储统一走 `prerequisites` 通用表（`object_type + object_id → prerequisite_type + prerequisite_id`），两种内容区共用
- 唯一的自校验：不允许自己指向自己（表级 CHECK 已存在）

### 4.4 object_type 枚举（**全站统一，以此表为准**）

| 值                      | 含义              | 对应表                 |
| ---------------------- | --------------- | ------------------- |
| `video`                | 旧单视频（兼容历史，不再新建） | `videos`            |
| `track_point`          | 单曲目             | `track_points`      |
| `track_collection`     | 曲谱集             | `track_collections` |
| `track_part`           | 曲目分 P           | `track_parts`       |
| `knowledge_point`      | 单知识点            | `knowledge_points`  |
| `knowledge_collection` | 知识点集            | `knowledge_collections`    |
| `knowledge_part`       | 知识点分 P          | `knowledge_parts`          |
| `library_resource`     | 图书馆资料           | `library_resources` |

> ⚠️ 命名定稿（2026-09-11 晚）：**两区命名完全对称**——曲目区 `track_point` / `track_collection`，知识点区 `knowledge_point` / `knowledge_collection`；**数据库表名同步重命名，禁止一切简写**（`kp_*` 前缀已废除，表已改名为 `knowledge_*` / `track_*` 全称）。早期用过的 `track` / `collection` / `kp_collection` / `kp_part` 全部作废。前后端代码已按本表完成重命名，旧库直接清空重建（M0 约定）。新增接口前先核对此表。

### 4.5 附件与资料

两类不同的东西，不要混：

| 类型    | 归属              | 表                                                                         | 说明                            |
| ----- | --------------- | ------------------------------------------------------------------------- | ----------------------------- |
| 内容附件  | 挂在单课/合集下，随详情页展示 | `content_attachments`（object_type + object_id）；旧 `video_attachments` 保留兼容 | PDF / GP / MP3 / PNG 等，逐个下载   |
| 图书馆资料 | 独立资料库，可被内容关联    | `library_resources` + `library_resource_links`                            | 有独立浏览页与上传页；详情页右下「关联图书馆」展示关联状态 |

**合集关联图书馆资料（新增规则）：**

- 合集支持关联一个或多个图书馆资料；曲目集使用 `object_type = track_collection`，知识点集使用 `object_type = knowledge_collection`。
- **不在 `track_collections` / `knowledge_collections` 表中新增单个 `library_id` 字段**；合集关联记录统一写入已有的 `library_resource_links` 多对多表。
- 合集关联属于合集自身的直接关联。合集内单课/单知识点通过所属合集获得**继承关联**，不复制单课关联记录。
- 单课/单知识点详情页及编辑页的图书馆资料区域必须**置顶展示**，展示结果为：自身直接关联资料 + 所属合集继承资料，按资料 ID 去重。
- 继承资料在单课/单知识点编辑页中以灰显状态展示，禁止删除；需要修改时必须进入对应合集编辑。
- 同一资料既被单课/单知识点直接关联、又被所属合集关联时只展示一份，并标注来源为「直接关联 + 来自合集」。
- 单课/单知识点移出合集后，仅解除该合集带来的继承关联；其自身直接关联继续保留。

### 4.6 P 命名与展示规范（布置作业搜索依赖）

**背景**：布置作业要能搜到并精准选中某个 P（如卡农里的「基本功练习」）。P 名单独看（「基本功练习」）无法知道属于哪首曲子，因此**所有跨上下文的 P 展示与搜索场景，一律拼接父级名**：

```
显示名 = 单课名-P名        例：卡农-基本功练习
                            1645 和弦进行-击弦练习
```

- **存储**：`track_parts` / `knowledge_parts` 的 `name` 只存 P 名本身（如「基本功练习」），**不存拼接结果**；拼接在展示层做
- **必须拼接的场景**（否则 P 名有歧义）：
  1. 布置作业的推送对象搜索结果（§5.8）
  2. 学员首页 / 历史作业的**单 P 作业卡片标题**
  3. 老师删除/取消作业时的确认提示
- **不拼接的场景**（上下文已有父级）：
  1. 单课详情页右侧 P 播放列表（已在卡农页面内，只写「基本功练习」）
  2. 新建/编辑单课时的 P 管理行
- 分隔符固定半角 `-`；P 名与单课名之间不再加空格
- 搜索匹配规则：搜「卡农」能命中其所有 P；搜「基本功练习」也能命中，结果里显示「卡农-基本功练习」

### 4.7 视频清晰度（自动转码 + 多档播放）

**方案定稿：教导主任只上传原画文件，服务端自动转码出 1080p / 720p，播放器手动切换档位。**

- **档位枚举（固定三种，全站统一）**：

| quality 值 | 含义       | 来源                                   |
| ---------- | ---------- | ------------------------------------ |
| `source`   | 原画         | 上传时的原始文件，**必传，上传完成即可播**    |
| `1080p`    | 高清 1080p | **服务端自动转码生成**，默认播放档        |
| `720p`     | 流畅 720p  | **服务端自动转码生成**                  |

- **数据模型**：新增表 `video_renditions`（`video_id → videos.id` ON DELETE CASCADE、`quality`、`video_url`、`file_size`、`status`，`UNIQUE(video_id, quality)`）；`status ∈ ready / processing / failed`；`videos.video_url` 保留为原画档，**旧路径不受影响**
- **转码实现（定稿：用腾讯云数据万象 CI，不自建转码）**：
  - COS 本身不带转码；**开通数据万象（Cloud Infinite）并绑定存储桶**后即可用其媒体处理能力（付费服务，有少量免费额度，超出按转码时长计费）
  - 在 CI 控制台建 **1080p / 720p 两个自定义转码模板** + 一条**数据工作流**（绑定 `videos/` 输入路径）——文件上传到该路径即**自动触发转码**，产物自动保存到约定输出路径（`videos/{videoId}/{quality}/`），**无需自写 ffmpeg**
  - 后端只做**胶水**：接收 CI 工作流的**业务回调**（或轮询任务状态），把对应 rendition 置 `ready` / `failed`；CI 回调接口用现有鉴权（签名校验）
  - **服务状态与转码解耦**：CI 不可用 / 未开通时，系统照常工作，只是只有原画档（原画永远可播）
- **播放器交互**（详情页通用模板 §3.3）：
  - 档位菜单**只列 `ready` 的档位**，当前档高亮；**默认播放 1080p**
  - 1080p 尚未转出（processing）时**回退原画播放**，转出后刷新页面可切
  - 切换档位**保留 currentTime 与播放状态**，不重新加载页面
- **规则与边界**：
  - 转码产物为渐进式 MP4，**不做 HLS/DASH 码率自适应**，切换即换文件地址
  - 删除 video 时 renditions 级联删除，COS 对象（含各档产物）沿用现有删除一致性链路逐一清理
  - 转码是尽力而为的增强功能：**转码失败或 CI 未开通不阻塞上传与播放**（原画永远可播）
  - 附件、封面与清晰度无关
  - **运维前置（控制台操作，非代码）**：① 开通数据万象并绑定存储桶；② 建 1080p/720p 转码模板；③ 建工作流绑定 `videos/` 路径并配置业务回调 URL

### 4.8 内容删除与作业快照策略（2026-09-12 定稿）

- **物理删除**：内容（视频/单课/合集/知识点/曲谱/电子书资料）删除即真删（库记录 + COS 对象），无回收站、无「已失效」占位态；删除入口一律**二次确认**。
- **引用直接消失**：删除时级联清理 `track_collection_items` / `knowledge_collection_items`、`prerequisites`、`content_attachments`、`library_resource_links` 中的关联记录，合集收录数等计数随之重算，不留任何残留标记。
- **作业零引用快照**：`user_assignments` 推送时即固化**标题快照**（含类型标识）、作业内容、练习要求、提交要求及布置时间，此后与源内容无任何关联；源内容删除不影响历史作业记录本身：
  - 学员端「今日作业」：按内容是否存活实时过滤，被删项直接消失；全部被删即显示空态；作业内容、练习要求、提交要求分栏展示，空栏不占位。
  - 学员端「我的历史作业」与老师/教导主任学生管理页的「历史作业」：读取同一份 `user_assignments` 数据，按 `operation_id` 聚合、按时间倒序组装，字段和内容口径一致；管理端为纯文本浏览、无点击行为，学员端对仍存活的内容保留既有点击跳转能力。
  - 三类页面均保留练习要求与提交要求的原始换行；每个栏目最多展示 3 行，超出时仅栏目内部滚动。
- **删除操作日志**：物理删除无回收站、不可撤销，所有删除操作需写日志（时间/操作人/对象），作为唯一追溯手段。
- **无学习行为统计**：全站不统计学习进度、观看时长等任何收看数据（见 §9）。

### 4.9 表单与文件边界校验（2026-09-13 定稿，**所有写接口必须落地**）

**执行原则（适用于全站所有校验）：**

1. **后端为权威**：每条规则在对应接口独立校验；前端 `maxlength` + 提交前校验只做体验层，**不能相信前端上报的任何数据**
2. **文件大小必须后端复核**：直传场景前端选择即拦，后端在 `upload-url` 签发与 complete 登记两处再次校验；complete 时以存储侧 **HeadObject 拿到的实际大小为准**（`storage.js` 已有该能力），超限拒绝并清理已传对象
3. 字数按**字符数**计（中英文均计 1），trim 后判空；大小单位 1MB = 1024×1024 字节
4. 错误提示逐字友好：「请填写 XX」「XX 不能超过 N 字」「XX 不能超过 N MB」

**单课（单曲目 `track_point` / 单知识点 `knowledge_point`）：**

| 字段 | 规则 |
| ---- | ---- |
| 标题 | 必填，≤ 80 字 |
| 简介 | 选填，≤ 800 字 |
| 封面 | 必填，1:1，≤ 10MB，仅 jpg / png / webp |
| 分 P | **新建时至少 1 个 P**；编辑/删 P 不允许删到最后 0 个 |
| P 名 | **必填**，≤ 50 字 |
| P 视频 | 每个 ≤ **2GB**，仅 mp4 / mov |
| 附件 | 每个 ≤ 100MB；**格式与数量不设限** |

**合集（曲谱集 / 知识点集）：**

| 字段 | 规则 |
| ---- | ---- |
| 标题 | 必填，≤ 80 字 |
| 简介 | 选填，≤ 800 字 |
| 封面 | 必填，1:1，≤ 10MB，仅 jpg / png / webp |
| 收录内容 | **允许为空**（0 个单课也可保存） |

**图书馆资料（`library_resource`）：**

| 字段 | 规则 |
| ---- | ---- |
| 标题 | 必填，≤ 80 字 |
| 简介 | 选填，≤ 800 字（与单课统一口径） |
| 封面 | 必填，≤ 10MB，仅 jpg / png / webp |
| 文件 | ≤ 500MB，格式不设限 |

**账号（学员 / 老师 / 教导主任）：** 见 §2.4——昵称 ≤ 10 字且仅中文/字母/数字/下划线；账号纯数字不限位数、全局唯一；密码 5~30 位。

**已有规则保持不动：** 班级名 ≤ 100 字、练习要求 ≤ 1000 字、提交要求 ≤ 1000 字、删除原因 ≤ 200 字、单次推送 ≤ 5 个对象（见 §5.8）。旧「留言」字段及兼容接口仅保留历史数据读取，不作为新页面输入。

#### 5.1.5 规则与边界

- 一个曲目可进入多个曲谱集；删除曲谱集**不得**删除曲目本身
- 删除曲目必须走现有删除一致性链路（**先删 COS 对象再删库记录**），禁止只删库
- P 的序号 `part_no` 在同一曲目内唯一（表级 UNIQUE），调整顺序时需避免中间态冲突
- 合集关联图书馆资料后，所有收录曲目详情页的「关联图书馆」区域置顶展示该资料；单曲不需要重复关联
- 单曲编辑页的关联资料区域置顶展示：单曲直接关联可编辑；来自合集的继承关联必须灰显并禁止删除，提示前往对应合集编辑
- 单曲后来加入已关联资料的合集时自动继承；从合集移除时仅解除该合集继承，单曲自身直接关联继续保留；仍属于其他已关联合集时继续继承
- 单曲详情页展示单曲直接关联与所属合集继承关联的并集，按资料 ID 去重并标注来源；同一资料两种来源同时存在时显示「直接关联 + 来自合集」
- 详情页不记录任何播放状态，**不新增进度表**

#### 5.1.6 验收标准

1. 首页上下两区正确显示；一条搜索框同时命中曲目名与曲谱集名；两区可独立排序，默认更新时间倒序
2. 点曲目进详情页，P 列表可切换播放；从曲谱集内点曲目同样进入
3. 同一曲目出现在多个曲谱集中互不影响；删除曲谱集后曲目仍在
4. 详情页右列三盒齐备；P 列表无进度条、无已看标记
5. 封面 1:1；P 无封面上传入口
6. 老师看不到任何新建/编辑/删除按钮；直接调写接口返回无权限
7. 视觉与 `tracks-home.html` / `track-point-detail.html` 逐块一致
8. **点曲谱集卡片进的是曲谱集详情页**（不是直接进某首曲目）；集内卡片点击才进单曲目详情
9. 教导主任在曲谱集详情悬停集内曲目卡片可见 查看详情/编辑/删除；删除两段确认，选「移出本合集」后卡片消失且曲目仍能单独搜到，选「彻底删除」后曲目连同视频一并清除

  5. 两个要求框保留换行；超过 3 行时仅对应框内部滚动，不撑高整体布局
  4. 停用态文案逐字正确，且不影响浏览与下载
  5. 老师/教导主任/游客访问 `/` 不被渲染为学员首页（按角色重定向）

### 5.10 我的历史作业

**状态**：✅ M8 已完成——页面 `frontend/app/my-homework/page.js`（CSS Module）与接口 `GET /api/user/assignments/history` 均已实现。

- **目标**：学员查看历次收到的作业
- **入口与权限**：仅学员（页头「我的历史作业」）
- **页面与交互**（参照 `my-homework.html`）：按 `operation_id` **聚合**展示历次作业；每条记录按栏目显示作业内容、练习要求、提交要求、布置时间、老师姓名及删除信息。该历史记录组件与 §5.6 学生管理页中老师/教导主任看到的历史作业保持同构，不能另造一套字段或排序规则。
- **数据与接口**：基于 `user_assignments` 按 `operation_id` 聚合；`GET /api/user/assignments/history` **已实现**（user-auth.routes.js）。管理端 `GET /api/admin/users/:userId/assignments` 复用同一查询/组装服务，仅按权限确定 userId 与展示能力。
- **角色差异**：学员只能查看自己的历史作业；对仍存活的内容可按 §5.8 点击跳转。老师/教导主任可查看所选学生的同一历史记录，但历史条目纯浏览不可点击；两端都保留练习要求和提交要求原文及换行。
- **规则与边界**：同一天多次布置按独立 operation 展示，不按日期合并；三栏均为空的记录不应存在；软删除记录是否展示按页面既有规则统一为不进入正常历史列表，但删除审计信息由管理端接口保留；不显示学习进度。
- **验收标准**：
  1. 学员历史作业与老师/教导主任学生管理中的历史作业记录数量、排序、栏目内容一致
  2. 历次作业按 operation_id 聚合、时间倒序展示，同一天多次布置不覆盖
  3. 作业内容、练习要求、提交要求三栏独立展示，空栏不占位，换行保留；学员首页仅将后两栏渲染为「练习要求」和「提交要求」两个框
  4. 学员可按既定规则点击仍存活内容，管理端历史记录不可点击
  5. 停用态文案逐字正确，非学员访问被拦截
